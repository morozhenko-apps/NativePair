## Initial OBEX probe defect

The first two probe revisions used short-lived `busctl` processes for `CreateSession`. BlueZ associates an OBEX session with the D-Bus connection that owns it, so the session disappeared when that process exited.

That produced misleading diagnostics such as:

- `session_created=yes`;
- `session_interfaces=none`;
- `target_interface_present=no`.

Those results are retained as diagnostic history but are not protocol evidence.

## MAP event probe

Two initial 60-second MAP event observation windows completed with:

- MAP session established;
- BlueZ MAP client active;
- no new `Message1` proxy observed;
- result: `inconclusive`.

The first event probe revision could only prove that BlueZ attempted notification registration as part of MAP session setup. BlueZ 5.85 does not expose a separate public D-Bus method for this registration, and its MAP driver does not propagate the registration result through `MessageAccess1`.

The enhanced probe therefore also checks:

- whether the local MNS UUID is advertised by the Linux adapter while the MAP session is active;
- whether the automatic notification-registration OBEX transfer is observed;
- whether that transfer reaches `complete` or `error`.

No MAP event capability conclusion is drawn from the two initial windows until this registration diagnostic is known.

### First local MNS diagnostic

The first local MNS probe reported:

- `obexd` service available;
- BlueZ `ProfileManager1` available;
- `obexd` process running;
- MNS not explicitly disabled through `--noplugin`;
- MNS name signature not found in the running `obexd` binary;
- local MNS controller UUID not visible;
- local SDP query failed, so SDP record presence remained unknown.

Upstream BlueZ 5.85 builds the MNS server into `obexd` whenever OBEX support is enabled. Because the installed Ubuntu package clearly provides working MAP/PBAP client functionality, the initial one-string binary test is not sufficient to conclude that Ubuntu omitted MNS.

The next probe revision checks independent binary signatures for:

- MAP client notification registration: `x-bt/MAP-NotificationRegistration`;
- MNS server event reception: `x-bt/MAP-event-report`;
- MNS server name string.

The second local MNS probe showed the opposite and more useful result:

- MAP client notification-registration signature present;
- MNS event-report signature present;
- MNS server name signature present;
- MNS server therefore compiled into the installed `obexd`;
- controller MNS UUID still not visible;
- local SDP query unavailable.

This pattern closely matches upstream BlueZ issue #2315, opened against BlueZ 5.85 on Ubuntu 26.04. In that defect, `obexd` installs the BlueZ name watch before `obex_server_init()` has populated the server-profile list. If `org.bluez` is already present, the callback can run against an empty list and no server profiles are registered for the lifetime of that `obexd` process.

The upstream workaround is to keep `obexd` running and restart `bluetoothd` once. The second `org.bluez` appearance then triggers profile registration after the list is populated.

NativePair treats this as an external BlueZ 5.85 environment defect, not a Pixel MAP limitation.

### BlueZ #2315 workaround verification

The upstream workaround was applied while `obexd` remained running:

```bash
sudo systemctl restart bluetooth
```

After the restart:

- local MNS UUID `00001133-0000-1000-8000-00805f9b34fb` became visible;
- OBEX Object Push UUID `00001105-0000-1000-8000-00805f9b34fb` also became visible;
- the NativePair diagnostic changed from the known #2315 pattern to `known_bluez_2315_pattern=no`.

This reproduces the upstream issue and verifies its workaround on the reference Ubuntu 26.04 host.

The subsequent MAP event probe still did not observe a notification-registration transfer through `obexctl`.

The privacy-safe remote MAP SDP probe then confirmed all attributes required by the BlueZ 5.85 MAP client:

- MAP MAS record found;
- `MASInstanceID` (`0x0315`) present;
- `SupportedMessageTypes` (`0x0316`) present;
- `MapSupportedFeatures` (`0x0317`) present.

This proves that the BlueZ MAP client has the prerequisites needed to queue `x-bt/MAP-NotificationRegistration`.

Source review also explains why the earlier observer can miss it: BlueZ registers the internal `Transfer1` object, performs the small notification-registration PUT, and unregisters that object immediately when the queued request is freed. The event probe therefore now starts a low-level `busctl monitor` before session creation. Raw monitor output remains temporary and is never printed.

### Successful MAP event delivery

The low-level event probe then observed:

- MAP session established;
- notification-registration `Transfer1` observed;
- explicit transfer completion status not captured;
- a new incoming SMS caused a new `org.bluez.obex.Message1` object to appear;
- no message properties or personal payload were read or printed.

Result: **MAP event path proven at evidence level 5**.

The successful event is stronger evidence than the missing explicit transfer completion status: an incoming MAP event cannot reach BlueZ's `Message1` path unless notification registration was effective.

A runtime inconsistency was also observed: one successful event run reported `local_mns_profile_advertised=no` even though the incoming event was delivered. Controller UUID visibility is therefore tracked as an environment/recovery diagnostic and is not treated as an authoritative runtime prerequisite once end-to-end event delivery has been demonstrated.

### First MAP send attempt

The first guarded MAP send attempt reached `PushMessage` and returned a transfer object, but the transfer ended in `error`.

This attempt is **not** treated as Pixel capability evidence because the probe itself contained a bMessage framing defect: it constructed the `BEGIN:MSG ... END:MSG` block through Bash command substitution. Bash strips trailing newline characters from command-substitution output, which removed the final LF from the required CRLF after `END:MSG`.

The probe was corrected to write the message block directly, compute `LENGTH` using the same byte-count rule as Android's MAP bMessage builder, and reject malformed CRLF framing before any `PushMessage` call.

### Successful MAP push transfer

The corrected send probe then observed:

- MAP session established;
- SMS_GSM advertised by the session;
- `telecom/msg` selected successfully;
- generated bMessage passed the local CRLF structure guard;
- `PushMessage` accepted by BlueZ;
- a transfer object returned;
- transfer status reached `complete`.

This proves the Linux-to-phone MAP push transport path.

Human verification then confirmed that the intended recipient received exactly one SMS with the expected fixed probe text. No duplicate was observed.

Result: **MAP outgoing SMS send path proven at evidence level 5**.

## BlueZ mpris-proxy crash

During an early MAP attempt, the Ubuntu `mpris-proxy` user process terminated with SIGSEGV.

Observed package:

- `bluez/5.85-4ubuntu0.2`.

This is tracked separately from NativePair's MAP/PBAP result. Controlled reruns were performed with `mpris-proxy.service` inactive. The unit's failed state was cleared with `systemctl --user reset-failed mpris-proxy.service`.

NativePair must not depend on disabling `mpris-proxy`; this remains a feasibility-only workaround for the affected distro package.
